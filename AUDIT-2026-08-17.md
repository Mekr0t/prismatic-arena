## 1. Executive summary

> **Read this section as of 2026-08-17.** All three headline problems below — the lent-out API key, the cluster stage's memory, and the fictional rank dimension — have since been **fixed and verified**; so has the merge carry-overlap defect named at the end. The prose is left in its original present tense as the record of what the audit found. For current state read the revision banner, the ✅ markers in §2, and §4. The one headline that is still open is the meta fragmentation — and it is a *different* defect from the carry-overlap one described here (recall, not precision).

The codebase is unusually disciplined for a solo project — `tsc --noEmit` is clean under `strict`, `eslint` reports zero errors, every SQL statement is parameterised, there is no XSS surface, and `SYSTEM_MANUAL.md` is a genuinely accurate architecture document. The problems are not sloppiness; they are three structural gaps that the data has now outgrown.

**First, the app lends out its Riot API key to anonymous callers.** Match IDs from the URL are interpolated into upstream request paths without encoding, so `..%2f` traversal and `?` injection let anyone aim the server's credentialed requests at arbitrary Riot endpoints; separately, `/api/profile/…` fires up to ~23 live Riot calls per request with no rate limit, which on a dev key (100 req / 2 min) is a five-request denial of service against the app's own crawler. **Second, the pipeline no longer fits in memory:** the cluster stage loads all 5.57 M `participant_units` rows into Node (measured ≈ 2.2 GB of heap for that array alone) and then issues 175 k sequential inserts inside one transaction. **Third, the rank dimension is fiction** — all 646,908 boards are labelled `challenger` by a column default while the crawler snowballs through every participant of every match it fetches (255,914 accounts discovered, 15,844 crawled), so the "Challenger" filter on the tier list describes a sample that is nothing of the kind.

Two more things deserve headline space. Roughly **half the participant tables holds matches nothing reads** — 40,531 of 82,692 stored matches (49 %) are Double Up / Normal / event queues that every downstream stage filters out, accounting for 2,738,883 of 5,571,250 unit rows. (That costs *storage and write throughput*, not API quota — see the correction above.) And the merge stage the user already flagged does have a concrete defect worth fixing before more tuning: when no carry clears the dominance rate, `getDomCarries` falls back to a *single* carry, which collapses the carry-overlap term to a binary 0-or-1 and simultaneously unlocks the "strong carry" slack — precisely the shape that produces merge behaviour with no middle ground.

Nothing here is unrecoverable, and most of it is a day or two of work each. What stands out reading the planning docs alongside the code is that the highest-severity findings are mostly **commitments the project made to itself and then drifted from** — the foundation plan specified a rank-gated frontier, the roadmap made "every stat carries its rank band" a north star, the frontend spec made a visible keyboard focus ring part of the quality floor, and the assumptions section scoped the crawl to ranked only. Those four are the ones I'd weight heaviest, because the project already decided they mattered.

## 5. Longer-term recommendations

**Fix the sample before tuning the model.** The merge algorithm is being tuned against data whose rank dimension is a constant and whose crawl frontier snowballs indiscriminately through Normal and Double Up lobbies. Real per-board rank buckets (finding R1) and a ranked-only crawl will change the input distribution enough that some current threshold tuning will need redoing — better to absorb that now than after another tuning cycle. This is also the cheapest way to make R7 ("stale-data illusion") true rather than aspirational: the ops panel already computes job staleness, it just has nothing to alert with.

**Give archetypes a stable identity.** `meta_comp` is doing three jobs at once: merge output, downstream grouping key, and public URL. A small `archetypes` table with a surrogate id, a stable natural key, and the current label as a *display* column decouples those, fixes link rot, and makes it possible to track an archetype's history across merge runs — which is what the trend feature actually wants.

**Introduce a caching layer between the services and the pages.** `unstable_cache` keyed on the selection tuple, invalidated by the rollup/merge stages via `revalidateTag`, turns a ~1 s page into a ~10 ms one and removes the pool-saturation ceiling. This is the single highest leverage change for the read plane and it does not require touching any query.

**Chain the pipeline explicitly.** The current "independent idempotent stages converge" model is elegant but no longer holds now that cluster prunes rows rollup depends on. Either flow-control the stages (BullMQ Flows exist for exactly this) or take a shared advisory lock.

**Add a decision trace to the merge.** Given how much tuning this stage will keep absorbing, being able to ask "why is comp 12345 in archetype X, and what was the runner-up?" from the admin inspector — rather than by re-running `merge-eval` locally — will pay for itself quickly.

**Then the platform basics, in order:** a CI workflow (typecheck/lint/test), a `docker-compose` for the two data dependencies, boot-time env validation, structured logging, and security headers. None are urgent while this is single-operator; all are prerequisites the first time someone else needs to run or deploy it.

**Retention policy.** `comp_stat_trends` (192 k rows/day, no pruning) and the non-ranked half of `participant_units`/`participant_traits` (2,738,883 unit rows, ~1 GB per table) are what will force a storage decision first.
